# Baseball Intelligence — 專案設計

本文件記錄目前「已經確定」的專案目標與設計原則。
尚未討論或尚未決定的事項，會明確標記為未決定，不預先寫成規格。

最後更新：專案初始化階段

---

## 1. 專案目標

**從數據中找到球隊值得注意的資訊。**

不是做一份完整的數據報表，而是從資料中挑出「分析人員應該知道」的事情，
並且能說明為什麼值得注意。

## 2. 使用情境（MVP）

| 項目 | 內容 |
| --- | --- |
| 使用者 | 球隊數據分析人員 |
| 案例球隊 | 富邦悍將 |
| 資料範圍 | CPBL |

## 3. 系統未來希望分析的三個方向

1. **球隊目前近況**
2. **特別需要注意的球員**
3. **下一場對手**

這三個方向是 MVP 的範圍界線。目前不擴大到選秀、養成、合約、傷兵管理等主題。

## 4. Insight 的定義

一則 insight 只有同時具備以下三件事，才算完成：

1. **數據佐證** — 說得出這個結論是從哪些資料、哪些計算得出來的
2. **與下一場比賽的關聯** — 說明它為什麼跟接下來的比賽有關
3. **決策支援** — 能導向一個可以思考或執行的方向

只有數字沒有關聯性的，是報表，不是 insight。
只有說法沒有數據的，是猜測，不是 insight。

## 5. 核心設計原則

### 5.1 Insight 必須有實際資料證據支持

任何輸出的結論，都必須能追溯回實際資料。無法追溯的結論不輸出。

### 5.2 不可以讓 LLM 自行捏造數據

模型不負責產生數字。所有數值一律來自資料與計算結果。

### 5.3 事實計算與語言解釋分離

| 層 | 負責 |
| --- | --- |
| 計算層（Python / SQL / 分析程式） | 計算事實，產出 evidence |
| 解釋層（未來的 LLM） | 只解釋已經計算好的 evidence |

這是本專案最重要的架構決定。解釋層不能繞過計算層直接取用原始資料，
也不能在解釋過程中新增計算層沒有算出來的數字。

註：解釋層目前**還沒有實作**，本階段也不會實作。

### 5.4 資料粒度

MVP 以 **Game（比賽）** 與 **Plate Appearance（打席）** 層級為主要粒度。

**不假設可以取得逐球（pitch-by-pitch）資料。** 任何分析設計都不能以逐球資料為前提。
若之後確認可取得逐球資料，再視情況擴充。

## 6. 目前的範圍界線（本階段刻意不做）

- 不建立 API client
- 不抓取 CPBL 資料
- 不建立資料庫
- 不加入 Flask / FastAPI / React
- 不加入 OpenAI API 或其他 LLM API
- 不加入 dashboard
- 不產生假的棒球資料
- 不新增尚未討論過的功能

## 7. 尚未決定的事項

這些項目目前是開放問題，需要先確認資料來源才能往下設計：

- 資料來源：實際可取得的 CPBL 資料從哪裡來、以什麼形式提供
- 可用欄位：Game 與 Plate Appearance 層級實際能拿到哪些欄位
- 資料更新方式：一次性取得、定期更新，或手動匯入
- 儲存格式：暫定以檔案為主（`data/raw`、`data/processed`），但尚未確定格式
- 「值得注意」的判定標準：用什麼指標、什麼門檻來判斷一件事值得注意
- Insight 的輸出形式

| 路徑 | 用途 |

| `data/processed/` | 整理後的資料，不進版控，目前為空 |
